# Prediction Result Visibility

## Goal

試合前の未投票ユーザーには勝敗予想の集計結果を開示せず、投票後に結果を確認できるようにする。
未投票時は PC / SP ともに「投票すると予想を確認できます」と表示し、既存の投票モーダルへ誘導する。

## Background / Context

現在の `/api/match/prediction` は認証・投票状態に関係なく集計値を返している。
フロントエンドも取得した集計値を常に描画するため、未投票ユーザーが他ユーザーの予想を確認してから投票できる。

投票後の結果開示によって他ユーザーの予想による先入観を抑えつつ、試合当日以降は過去コンテンツとして誰でも結果を確認できる状態を維持する。

## Scope

### In Scope

- 試合前は、対象試合へ投票済みのユーザーまたはゲストにだけ集計結果を返す
- 試合当日以降は投票状態に関係なく集計結果を返す
- 未投票時の API レスポンスで、集計結果が非公開であることを明示する
- PC / SP 共通で「投票すると予想を確認できます」と表示する
- 未投票表示に赤・青の控えめなグラデーションとぼかしを CSS で適用する
- SP ではカードの高さと余白を抑え、投票ボタンを 44px 以上のタップ領域で表示する
- API と UI の状態分岐をテストする

### Out of Scope

- 投票内容の変更・取消機能
- 投票締切ルールの変更
- DB スキーマ変更
- 過去試合での集計非公開
- 勝敗予想以外の画面デザイン変更

## Impact Area

- 試合別勝敗予想取得 API
- 勝敗予想 Service / Repository / Resource
- フロントエンドの勝敗予想レスポンス型
- 試合詳細画面の勝敗予想サマリー
- 勝敗予想 API Hook
- バックエンド Feature Test
- フロントエンド Component / Hook Test

## Options

### Option 1: フロントエンドだけで未投票時に非表示

- メリット: 変更が小さい
- デメリット: API を直接呼ぶと集計結果を取得できる
- リスク: 仕様として非公開を保証できない

### Option 2: API が投票状態と試合日を判定して公開可否を返す

- メリット: API レベルで非公開を保証でき、フロントエンドも明示的な状態で描画できる
- デメリット: バックエンドとフロントエンドの両方に変更が必要
- リスク: 認証・ゲスト・試合日の境界条件をテストする必要がある

### Option 3: 未投票ユーザーには常に非公開

- メリット: ルールが単純
- デメリット: 試合後も未投票者が結果を確認できず、ゲスト Cookie 消失時の閲覧性も悪い
- リスク: 過去コンテンツとしての価値を損なう

## Decision

Option 2 を採用する。

## Rationale

投票前の集計結果を確実に非公開にするには、フロントエンドだけでは不十分である。
API が `isVisible` を返し、非公開時は票数を返さないことで、認証状態やキャッシュに依存せず仕様を保証できる。
試合当日以降は公開することで、投票機会を失ったユーザーやゲスト情報が失われたユーザーも過去結果を確認できる。

## Test Plan

- 試合前の未認証ユーザーには `isVisible: false` が返り、票数を返さない
- 試合前の未投票ユーザー・ゲストには `isVisible: false` が返る
- 試合前の投票済みユーザー・ゲストには集計結果が返る
- 試合当日以降は未認証・未投票でも集計結果が返る
- 未投票 UI では集計値を表示せず、共通文言と投票ボタンを表示する
- 投票済み UI では従来どおり票数・割合・自分の投票先を表示する
- 投票成功後に試合別集計を再取得する
- フロントエンドの関連 test / lint / build を実行する
- バックエンドテストは Docker 経由で実行する

## Risks

- React Query のキャッシュに以前の公開結果が残る可能性があるため、API の `isVisible` を描画条件として必ず使用する
- PHP の日時比較が時刻を含むため、既存の投票締切判定と同じ処理を利用して挙動を揃える
- ゲスト認証ガードと通常認証ガードの双方で投票有無を正しく判定する必要がある
- SP の高さを抑えすぎると文言が窮屈になるため、320px 幅でも折り返しと 44px 以上のタップ領域を維持する
