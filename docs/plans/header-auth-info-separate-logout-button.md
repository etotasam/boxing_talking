# Header Auth Info Separate Logout Button

## Goal

PC / SP の両方で、ユーザーアイコンとユーザー名を表示専用のユーザー情報として扱い、独立したログアウトアイコンボタンをクリックした場合だけログアウトできるようにする。

## Background / Context

現在の `HeaderAuthInfoView` は、ユーザーアイコン、ユーザー名、区切り線、ログアウトアイコンの全体を1つの `button` で囲んでいる。そのため、ユーザー情報もログアウト操作の一部に見え、ユーザーアイコンまたはユーザー名をクリックしてもログアウトが実行される。

また、PCではホバー時に「ログアウト」というポップアップ文言が表示される。採用するUI案Aでは、ユーザー情報とログアウト操作を明確に分離し、このポップアップは表示しない。

## Scope

### In Scope

- ユーザーアイコンとユーザー名を、クリック操作を持たない表示用グループに変更する。
- ログアウトアイコンを独立した `button` にする。
- PC / SP の両方でログアウトアイコンボタンを表示する。
- ログアウト処理はログアウトアイコンボタンのクリック時だけ実行する。
- スクリーンリーダー向けの `aria-label="ログアウト"` はアイコンボタンに残す。
- PCではユーザー情報とログアウトボタンの間に区切り線を表示する。
- SPでもPCと同程度の40pxユーザーアイコンとユーザー名を表示し、長いユーザー名は省略表示する。
- ログアウトボタンはPC / SPともに最低40px四方の操作領域を確保し、薄い枠線と角丸で独立した操作要素として示す。
- hover時は軽い透明度変化、キーボードフォーカス時は視認可能なフォーカス表示を設ける。
- ホバー時に表示される「ログアウト」のポップアップを削除する。
- 既存ユニットテストを新しいDOM構造とPC / SPの振る舞いに合わせて更新する。

### Out of Scope

- ログアウトAPI、認証・ゲスト判定、ログアウト後の遷移処理の変更。
- ヘッダー全体、ナビゲーション、ハンバーガーメニューのレイアウト変更。
- ユーザー情報へのプロフィール遷移など、新しいクリック操作の追加。
- ログアウト前の確認ダイアログ追加。
- アイコンライブラリやデザイントークンの変更。

## Impact Area

- 表示コンポーネント: `frontend/src/components/module/Header/component/HeaderAuthInfo.tsx`
- SP狭幅時の配置保護: `frontend/src/components/module/Header/component/HeaderView.tsx`
- ユニットテスト: `frontend/src/components/module/Header/__test__/HeaderAuthInfo.test.tsx`
- API、DB、バックエンド、状態管理、設定への影響はない。

## Options

### Option 1: 表示用グループと独立したアイコンボタンに分離する（採用）

- ユーザー情報を `div` などの非操作要素にする。
- ログアウトアイコンだけを `button` で囲む。
- PC / SPで同じDOM上の責務を維持し、レスポンシブクラスで表示サイズと間隔を調整する。

メリット:

- 見た目と操作範囲が一致する。
- HTMLの意味が明確で、キーボード操作とスクリーンリーダー対応を維持できる。
- ログアウト処理やフックを変更せず、表示層だけの小さな変更に限定できる。

デメリット・リスク:

- SPの限られた幅にログアウトボタン分の領域が必要になる。
- ユーザー名が長い場合のレイアウトを既存の非表示方針または省略表示で保護する必要がある。

### Option 2: 全体のボタンを維持し、クリック対象をCSSでログアウトアイコンに見せる（不採用）

- DOMは現在のままにして、見た目だけを分離する。

メリット:

- 差分が小さい。

デメリット・リスク:

- 実際のクリック領域は分離されず、要件を満たさない。
- ユーザー情報がログアウトボタンとして読み上げられる問題が残る。

### Option 3: ログアウトアイコンをクリック可能な `div` にする（不採用）

- `div` にクリックハンドラを付けてログアウトを実行する。

メリット:

- 見た目上の分離はできる。

デメリット・リスク:

- キーボード操作、フォーカス、buttonの標準動作を別途実装する必要がある。
- アクセシビリティと保守性でOption 1に劣る。

## Decision

Option 1を採用する。UIは採用済みの案Aに合わせ、`[ユーザーアイコン + ユーザー名] | [ログアウトアイコンボタン]` の構成にする。

PC / SPともに40px程度のユーザーアイコンとユーザー名を表示する。SPでは限られた幅に対応するためユーザー名を省略可能にし、区切り線は表示しない。どちらのデバイスでもログアウトボタンは最低40px四方とし、薄い枠線、角丸、hover / focus状態によって独立した操作対象であることを示す。常時表示するボタン文言やポップアップは追加しない。

## Rationale

- ユーザーが選択した案Aを最小の変更範囲で再現できる。
- 表示情報と破壊性を伴う操作の責務がDOM上でも分かれる。
- 既存の `onLogout` と認証・ゲスト分岐をそのまま利用でき、リグレッション範囲を表示層に限定できる。
- `button` とアクセシブルネームを使うことで、アイコンだけのUIでも操作目的を支援技術に伝えられる。
- PC / SPの公開される振る舞いを既存のVitestで直接保証できる。

## Test Plan

`frontend/src/components/module/Header/__test__/HeaderAuthInfo.test.tsx` を更新し、以下を保証する。

- PCの認証ユーザー時にユーザー名を表示し、ログアウトボタンから `logout` を実行できる。
- PCのゲスト時に「ゲスト」を表示し、ログアウトボタンから `guestLogout` を実行できる。
- 認証ユーザーでもゲストでもない場合は、ユーザー情報とログアウトボタンを表示しない。
- SPでもユーザー名を表示し、ログアウトボタンから `logout` を実行できる。

ログアウトボタンは各操作テストで `getByRole('button', { name: 'ログアウト' })` を用いて取得し、アクセシブルネームを個別テストとして重複させない。ユーザー情報の非操作要素化、ポップアップ削除、区切り線、操作領域などのUI構造・スタイルはユニットテストで固定せず、ブラウザ確認と実装後レビューで確認する。

実装後に以下を実行する。

- `cd frontend && npm test -- HeaderAuthInfo.test.tsx`
- `cd frontend && npm run lint`
- `cd frontend && npm run build`

代表的なPC / SP viewportでブラウザ表示も確認し、以下を保証する。既存Cypressで対象ヘッダーを安定して確認できる場合はCypressを利用し、難しい場合は開発サーバー上で手動確認して結果を報告する。

- ユーザー情報、区切り線、ログアウトボタンが案Aの順序で表示される。
- PC / SPでユーザーアイコン・ユーザー名をクリックしてもログアウトされず、ログアウトアイコンボタンをクリックした場合だけログアウトされる。
- SPでユーザーアイコン、ユーザー名、ログアウトボタンが重ならず、長いユーザー名が省略され、タイトル、ナビゲーション、ハンバーガーメニューなど他のヘッダー要素とも衝突しない。
- ログアウトボタンの操作領域がPC / SPともに最低40px四方である。
- hover / focus状態が確認でき、「ログアウト」のポップアップ文言は表示されない。

## Risks

- SPで40px程度のユーザーアイコン、ユーザー名、ログアウトアイコンを表示するため、ヘッダー内の利用可能幅が狭くなる。ユーザー名の省略表示、固定のタップ領域、適切な間隔で衝突を避ける。
- アイコンのみのボタンから `aria-label` を外すと操作目的が分からなくなるため、表示文言を削除してもアクセシブルネームは残す。
- PC用の条件分岐を移動する際、SPでログアウトアイコンまで非表示に戻さないようテストで保証する。
- ユーザー情報側にクリックハンドラやbutton要素が残ると要件を満たさないため、実装後の差分レビューとブラウザ確認で確認する。
