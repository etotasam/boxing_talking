# Redesign Prediction Vote Modal

## Goal

勝者予想モーダルを既存の試合詳細画面と統一感のあるダーク UI へ変更し、PC/SP の両方で選手選択から投票確定まで安全に操作できるようにする。

## Background / Context

現在の勝者予想モーダルは白背景と汎用ボタンで構成され、黒を基調に赤・青・黄をアクセントとする試合詳細画面から視覚的に分離している。また、選手ボタンを押した時点で投票が実行されるため、選択内容を確認する段階がない。

## Scope

### In Scope

- モーダルをダーク UI へ変更する。
- 赤・青コーナー別の選手選択行を縦に表示する。
- 選択状態をモーダル内で保持し、確定ボタンから既存の投票処理を呼び出す。
- 戦績、キャンセルボタン、王冠表示を削除する。
- 閉じる操作を右上の閉じるボタンに統一する。
- PC/SP で選手名と操作領域が崩れないレスポンシブ表示にする。
- 公開される選択・確定・閉じる動作をコンポーネントテストで保証する。

### Out of Scope

- 投票 API、投票成功・失敗時の処理変更。
- 試合詳細画面のモーダル外のデザイン変更。
- バックエンド、DB、投票結果表示の変更。

## Impact Area

- 勝者予想モーダルの表示コンポーネント。
- 勝者予想モーダル内のオーバーレイとダイアログ属性。
- 勝者予想モーダルの Storybook 表示。
- 勝者予想モーダル近傍の Vitest。

## Options

### Option 1: 選手選択時に即時投票する

- メリット: 現行処理をほぼ維持でき、実装量が少ない。
- デメリット: 選択内容を確認できず、承認済みモックの選択状態と確定操作を再現できない。
- リスク: 誤操作による投票を防げない。

### Option 2: 表示コンポーネント内に選択状態を持つ

- メリット: API 連携を変更せず、選択と確定を分離できる。UI 固有の状態を表示コンポーネント内に閉じられる。
- デメリット: 表示コンポーネントに小さな状態管理が追加される。
- リスク: 確定前の未選択状態と選択切り替えをテストで保証する必要がある。

### Option 3: Container に選択状態を持つ

- メリット: 表示コンポーネントを制御コンポーネントとして扱える。
- デメリット: API 連携を担当する Container へ一時的な UI 状態が入り、責務が広がる。
- リスク: 今回の小規模な選択状態に対して構造が複雑になる。

## Decision

Option 2 を採用する。

## Rationale

承認済み UI の「選択してから確定する」操作を満たしつつ、既存の投票 API と Container の処理を変更しないため、影響範囲が限定される。選択状態はモーダルを閉じると破棄される一時的な UI 状態であり、表示コンポーネント内で管理するのが責務と保守性のバランスに優れる。

## Test Plan

- 初期状態では投票確定ボタンが無効であり、投票処理が呼ばれないことを保証する。
- 赤または青の選手を選択すると選択状態が利用者に伝わることを保証する。
- 確定時に選択したコーナーだけが投票処理へ渡されることを保証する。
- 選手を切り替えた場合、最後に選択したコーナーが投票されることを保証する。
- 右上の閉じるボタンからモーダルを閉じられることを保証する。
- 戦績とキャンセルボタンが表示されないことを保証する。
- 関連 Vitest、ESLint、TypeScript/Vite build を実行する。

## Risks

- 長い選手名が SP 幅で折り返された際に、選択アイコンと重なる可能性がある。
- オーバーレイとダイアログ枠は現在の唯一の利用箇所へ統合し、用途が不明確な共通コンポーネントを作らない。
- 確定ボタンの無効状態が視覚だけでなく HTML 属性としても無効になる必要がある。
